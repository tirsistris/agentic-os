## Замечания к входным данным

1. **Backlog: один экран в `screens.md` vs два под-узла в sitemap `ia.md`.** Sitemap в
   `ia.md` перечисляет «Группы / Темы» и «Приоритизация (Value × Effort)» как два отдельных
   под-узла Backlog; User Flow (шаги 5–9) проходит их последовательно в рамках одного визита
   без явного указания смены экрана/URL. `screens.md` уже сам зафиксировал это расхождение
   (раздел «Заметки о противоречиях/пробелах входа», п.1) и решил собрать один Frame
   (split-view). Прототип здесь наследует это решение: шаги 5–9 ia.md все указывают на один и
   тот же Frame `Backlog`, без внутренних переходов между «под-экранами». Расхождение не
   правилось, только фиксируется повторно для прозрачности перед `ia-architect`.
2. **Login (ia.md User Flow, шаг 1) отсутствует как Frame.** `ia.md` формально ставит Login
   первым шагом главного сценария, но ни `screens.md`, ни этот прогон не создавали такой
   экран (жёсткий скоуп задания — 4 экрана, ни один из них не Login). Это не противоречие
   входных данных как таковое (`screens.md` сам явно отложил Login), но так как `ia.md`
   продолжает ссылаться на Login как на шаг 1 главного флоу, это создаёт разрыв на границе
   прототипа — задокументирован в «Известные ограничения» как переход за границей.
3. Расхождений в именах экранов между `screens.md` и `ia.md` не найдено — «Inbox», «Backlog»,
   «Roadmap» называются идентично (с поправкой на русские подписи в скобках), Settings тоже
   называется одинаково в обоих артефактах (просто не собран).

**Обоснование Animation = Instant (а не Move In) для переходов 4 и 9:**
Все 4 экрана используют один и тот же persistent shell (Top bar + Left sidebar, идентичные по
`screens.md` для Inbox/Backlog/Roadmap). Это не мобильный push-стек с полноэкранными
переходами, а desktop-приложение с фиксированной навигацией и меняющимся центральным
контентом — паттерн ближе к «tab switch», для которого правило анимаций прямо предписывает
Instant. Move In/Move Out (слева/справа) в этом контексте создавали бы иллюзию «отъезжающего
экрана целиком», включая statичный sidebar и topbar, что не соответствует происходящему на
самом деле (меняется только центральная зона). Поэтому по всей карте переходов (main flow и
navigation) используется единообразно Instant.

выдумывать обход»).

прогон.

## Как открыть прототип

Инструкция ниже — целевая, для следующего прохода с реальным Figma MCP-доступом (в этом
прогоне ничего не проигрывалось вживую):

1. Открыть Figma-файл проекта (URL пока не применимо — файл не создавался в этом прогоне).
2. Выполнить связи из разделов «Main flow» / «Navigation» через `use_figma` (Prototype tab)
   или руками через UI Figma — каждая помечена ⚠️ выше как ещё не созданная.
3. Выбрать Frame `Inbox (Входящие)` и пометить его как Flow Start.
4. Нажать Present (или клавишу D) на Frame `Inbox (Входящие)`.
5. Прототип пройдёт: Inbox → (Принять) → Backlog → (Добавить в роадмап) → Roadmap, плюс
   sidebar-переходы между тремя экранами в любом порядке. Переходы к Settings и обратно к
   Inbox-empty state кликом внутри прототипа недоступны (см. «Известные ограничения»).
6. **Веб-сборка прототипа:** в веб-версии прототипа добавляется служебная панель просмотрщика
   (переключатель 4 экранов) — мета-слой прототипа, не элемент UI продукта; решает
   недостижимость Inbox-empty кликом.

## Известные ограничения

1. **Документный проход, без живой проводки в Figma.** Ни один вызов
   `mcp__figma__use_figma` не выполнялся в этой сессии. Ни одна Prototype Connection/reaction
   физически не создана в Figma-файле, Flow Start не проставлен в самом Figma UI. Весь этот
   документ — спецификация для реализации при следующем проходе с write-доступом к Figma
   (remote MCP, OAuth, team-доступ — см. `CLAUDE.md` §MCP).
2. **В скоупе всего 4 экрана из полного sitemap `ia.md`.** Полный sitemap (`ia.md`
   §«Sitemap») содержит 4 верхнеуровневых раздела и 8 под-узлов: Inbox (2: «Все элементы»,
   «Без группы»), Backlog (2: «Группы/Темы», «Приоритизация»), Roadmap (1: «Kanban-вид»),
   Settings (3: «Интеграции», «Правила захвата», «Рабочее пространство и участники»). Кроме
   того, User Flow ссылается на Login (шаг 1) и Edge Case 3 — на 3-шаговый onboarding wizard,
   ни один из которых не входит в формальный sitemap, но упоминается в flow. Из всего этого
   объёма собраны и доступны для прототипирования только: Inbox, Inbox — Empty state, Backlog
   (единым экраном), Roadmap — то есть 4 Frame из потенциальных ~10+ экранов/состояний,
   описанных в `ia.md`. Это прямое наследование скоупа `screens.md` (§«Технический долг /
   Отложено»), не новое ограничение этого прогона.
3. **Переходы за границей прототипа (out-of-scope targets)** — зафиксированы явно, а не
   выдуманы обходным путём:
   - `Inbox — Empty state` → кнопка «Подключить Telegram» → **Settings → Интеграции**
     (ia.md Edge Case 1). Экран Settings не сгенерирован.
   - `Inbox (Входящие)` → кнопка «Настройки» в error-баннере «Telegram API недоступен» →
     **Settings → Интеграции** (ia.md Edge Case 2). Экран Settings не сгенерирован, сам
     error-баннер тоже не собран отдельным Frame/state.
   - Все 4 экрана → sidebar item «Settings» → **Settings** (общий пункт левой навигации).
     Экран не сгенерирован.
   - `Login` (ia.md User Flow шаг 1) → **Inbox**. Экран Login не сгенерирован; прототип в
     этом объёме стартует напрямую с Inbox (Flow Start), минуя авторизацию.
   - `Onboarding wizard` (ia.md Edge Case 3, 3 шага) — все шаги отсутствуют как Frame;
     переход wizard → Inbox с CTA «Разберите первую партию» не может быть проложен.
4. **Компонентные in-place состояния не собраны** — ряд шагов главного user flow (отклонение
   строки в Inbox, привязка к группе, простановка Value/Effort, ручной drag на матрице,
   drag-and-drop карточек в Roadmap) технически не меняют Frame, а меняют состояние
   компонента внутри одного Frame. Ни для одного из этих состояний в `screens.md` не собраны
   отдельные варианты компонентов (no variants), поэтому такие переходы не задокументированы
   как prototype connections, а помечены как tech debt в таблице «Main flow». Для реалистичной
   демонстрации потребуется отдельный проход `design-generator` с component variants
   (например, строка списка: default/dismissed; карточка группы: default/updated) — это не
   было решено «обходом» (например, фейковой связью к другому Frame), а явно оставлено
   незамкнутым.
5. **Нет прямой связи между `Inbox (Входящие)` и `Inbox — Empty state`.** Это два разных
   Frame, представляющих одно и то же логическое место в sitemap в разных состояниях данных
   (пусто / не пусто). Переход между ними в реальном продукте управляется наличием данных, а
   не действием пользователя внутри прототипа — поэтому click-triggered connection между ними
   намеренно не создавалась (не выдумывался фейковый триггер).
6. **Home-иконка / логотип в Top bar** не задокументирована как кликабельный элемент в
   `screens.md` (нет явного указания на действие) — connection на «главную» через логотип не
   добавлена, чтобы не выдумывать несуществующее поведение. Если логотип должен вести на
   Inbox, это нужно явно зафиксировать в `screens.md` при следующей итерации
   `design-generator`, после чего добавить сюда.
7. Расхождение между `screens.md` (Backlog как один экран) и `ia.md` sitemap (Backlog как два
   под-узла) — уже задокументировано `screens.md` самостоятельно; здесь только подтверждено
   повторно, входные файлы не редактировались.
8. **Переходы 4 и 9 (Main flow) — прототипная конвенция, не 1:1 с поведением продукта.** В
   реальном продукте действия «Принять» и «Добавить в роадмап» происходят in-place: элемент
   перемещается между разделами (Inbox → Backlog → Roadmap), но пользователь не покидает
   текущий экран/контекст. Переход на другой Frame добавлен в прототип намеренно — иначе
   сценарий «понедельничный разбор» нельзя было бы проиграть одним непрерывным путём по трём
   экранам. Это осознанное упрощение прототипа ради демонстрируемости флоу, а не описание
   реального поведения продукта.
