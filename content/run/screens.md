> **Режим прогона:** документный проход, без Figma. Никакие Figma MCP-инструменты не
> вызывались, ничего не рендерилось. Поля, существующие только при работе в Figma (Frame ID,
> Figma file URL, smoke-test в Figma UI), помечены ниже как «не применимо».

## Сводка

- **Target platform:** Desktop web. Определено однозначно из `brief.md` §«Ограничения»:
  «Платформа: веб-приложение (рабочее место PM) + интеграции в чаты (боты/приложения в
  Slack/Telegram/Discord как точка входа фидбэка)». Основной пользователь — PM за рабочим
  местом (research.md §3, персона Марина: «десктоп на работе, разбор по понедельникам»).
  Открытого вопроса по платформе нет — выбор не требовал угадывания.
- **Frame size (референс, не отрендерено):** 1440×900 — стандартный desktop web по таблице
  device sizes. Ниже структура описана в терминах зон (Top / Left / Center), не в пикселях,
  так как рендера не было.
- **Кол-во экранов:** 3 happy path + 1 edge case (жёсткий скоуп этой итерации, задан
  оркестратором). Остальные экраны из `ia.md` (Settings, Login, onboarding wizard, Error
  state) — см. «Отложено».
- **Figma file:** не применимо (документный проход).
- **Страница макетов:** не применимо (документный проход).
- **Frame ID (по каждому экрану):** не применимо (документный проход, ID не выдумывались).

## Экраны

### Screen 1: Inbox (Входящие)

- **Frame ID:** не применимо (документный проход)
- **Назначение:** Главный экран продукта (ia.md §«Главный экран»). Закрывает **JTBD-1** —
  «стянуть фидбэк из чата, не теряя» (research.md §4) — и частично **JTBD-6** — «отделить
  фидбэк от болтовни» (research.md §4; must-фича #2/#3 в таблице фич §7) через действие
  «отклонить как шум».
- **Main CTA:** «Принять фидбэк» — по каждому элементу списка (ia.md User Flow шаг 4:
  «Нажимает «Принять» на релевантном элементе» → элемент уезжает в Backlog). Вторичное
  действие на каждой строке — «Отклонить (шум)» (JTBD-6), оно не главное: оно снимает шум, но
  не продвигает элемент к цели пользователя.
- **Layout pattern:** F-pattern. Обоснование: это список входящих с регулярным
  сканированием сверху вниз (алгоритм design-generator явно относит списки/ленты к
  F-pattern); сценарий «понедельничный разбор» (research.md §5, персона Марина) — это
  просмотр десятков строк подряд, взгляд идёт построчно сверху вниз с быстрой проверкой
  источника/автора слева и действия справа.
- **Структура по зонам (Desktop: Top / Left / Center):**
  - **Top:** глобальная навигация — имя продукта, переключатель workspace («Команда

  - **Left:** side-навигация — Inbox (активен, бейдж с количеством непросмотренных),

### Screen 1.empty: Inbox — Empty state

- **Frame ID:** не применимо (документный проход)
- **Назначение:** ia.md Edge Case 1 (Empty State). Закрывает тот же JTBD-1, но в состоянии
  «до первого фидбэка» — задача экрана здесь не разбор, а **направление пользователя к
  действию, разблокирующему JTBD-1** (подключение интеграции).
- **Main CTA:** «Подключить Telegram» → ведёт в Settings → Интеграции (ia.md Edge Case 1,
  дословно: «Кнопка CTA: «Подключить Telegram» → ведёт в Settings → Интеграции»).
- **Layout pattern:** Inverted pyramid. Обоснование: нет данных для сканирования списком —
  экран должен сначала дать контекст («почему пусто»), затем свести взгляд к единственному
  действию; это классическая структура «контекст → действие», а не список/лента.
- **Структура по зонам:** тот же shell, что у Screen 1 (Top bar + Left sidebar с бейджем
  «0» на Inbox), но Center вместо списка показывает центрированный пустой стейт:
  - Top: без изменений (Top bar, Left sidebar)
  - Center: иконка/иллюстрация пустого инбокса → заголовок → подзаголовок → кнопка CTA
  - Bottom (опционально): вспомогательная ссылка «Как это работает?»
- **Ключевые блоки (сверху вниз):**
  1. Top bar + Left sidebar (Inbox активен, бейдж «0»)
  2. Иконка/иллюстрация (нейтральная, не декоративно-яркая — тон продукта деловой)
  3. Заголовок: «Пока нет фидбэка» (дословно из ia.md)
  4. Подзаголовок (вариант A — интеграция не подключена): «Подключите Telegram-бота, чтобы
     фидбэк из чатов автоматически попадал сюда»
  5. Кнопка CTA: «Подключить Telegram»
  6. **Контент-вариант B (интеграция уже подключена, но фидбэка нет)** — та же рамка экрана,
     другой текст вместо CTA: «Интеграция активна. Перешлите любое сообщение вашему боту —
     оно появится здесь» (без кнопки, т.к. действие происходит вне продукта, в Telegram).
     Оба варианта — часть одного edge-case экрана per ia.md (единый Empty State с двумя
     содержательными состояниями), не отдельный 5-й экран.
- **Плейсхолдер-контент:** тексты заголовка/подзаголовка взяты дословно из ia.md Edge Case
  1 — не переформулировались.
- **Решения с обоснованием:**
  - Два текстовых варианта (A/B) в одном макете, а не два отдельных Frame — ia.md описывает
    их как одно и то же место в sitemap («Inbox», один edge case) с условной веткой текста в
    зависимости от состояния интеграции, а не как разные экраны.
  - CTA убирается в варианте B — интеграция уже настроена, повторный призыв «подключить»
    был бы некорректен и противоречил бы состоянию системы.
- **Smoke-test:** не применимо (документный проход). Внутренняя проверка: оба текстовых
  варианта и CTA совпадают дословно с формулировками ia.md Edge Case 1.

### Screen 2: Backlog (группы + приоритизация Value×Effort)

- **Frame ID:** не применимо (документный проход)
- **Назначение:** Закрывает **JTBD-2** («не разбирать сотни сообщений руками» — через
  авто-группировку) и **JTBD-4** («привязать фидбэк к теме, видеть вес» — через счётчик
  частоты), а также **JTBD-3** («понять, за что браться» — через Value×Effort и ручную
  корректировку). Соответствие зафиксировано в ia.md таблице «Связь с JTBD из research.md».
- **Main CTA:** «Добавить в роадмап» — на топ-приоритетных группах (ia.md User Flow шаг 9:
  «Нажимает «Добавить в роадмап» на топ-пунктах» → элементы уезжают в Roadmap колонку
  «To Do»). Это единственное действие, которое реально продвигает пользователя к цели
  экрана (принять решение и отправить дальше); группировка и простановка Value/Effort —
  подготовительные действия к нему.
- **Layout pattern:** F-pattern для общей структуры страницы (сканирование списка групп
  сверху вниз слева, затем переход взглядом к матрице справа) — это dashboard-подобный
  экран с двумя виджетами, а не диалоговая форма или лендинг, поэтому Z/inverted pyramid не
  подходят. Сама Value×Effort матрица внутри — не самостоятельный layout pattern, а
  визуальный 2D-виджет внутри F-сканирования страницы.
- **Структура по зонам (Desktop: Top / Left / Center с двумя колонками):**
  - **Top:** тот же shell (Top bar)
  - **Left:** side-навигация, пункт «Backlog» активен
  - **Center-Left:** список групп/тем (карточки) — по одной на группу, с частотой
  - **Center-Right:** матрица Value (вертикальная ось 1–5) × Effort (горизонтальная ось
    1–5), группы нанесены как маркеры/карточки, размер маркера пропорционален частоте
- **Ключевые блоки (сверху вниз / слева-направо):**
  1. Top bar + Left sidebar (Backlog активен)
  2. Заголовок «Бэклог» + переключатель вида (неявный: обе панели видны одновременно, а не
     табами — обоснование ниже)
  3. Center-Left — список групп:
     - Карточка группы: название, счётчик частоты («×3»), мини-иконки источников
       (Telegram/Slack), бейдж «в роадмапе» (если группа уже добавлена в роадмап —
       симметрично бейджу «скорректировано вручную»), кнопка «Развернуть» (показать
       привязанные исходные сообщения)
     - Действие на карточке: «Привязать сообщение к группе» / «Создать новую группу»
       (ia.md User Flow шаг 6)
  4. Center-Right — матрица Value×Effort:
     - Оси: Value (1–5, вертикаль) / Effort (1–5, горизонталь)
     - Квадранты подписаны общепринятыми названиями лёгкого Value×Effort фреймворка
       («быстрые победы» — высокий Value/низкий Effort, «крупные ставки» — высокий
       Value/высокий Effort, и т.д.) — это устоявшаяся нотация метода, а не придуманная
       продуктовая механика
     - Маркеры групп на матрице, с возможностью ручного перетаскивания (ia.md шаг 8:
       «Ручной ранг зафиксирован; значок «скорректировано вручную»»)
     - Значок «скорректировано вручную» на маркерах, где ранг сдвинут руками
  5. Main CTA «Добавить в роадмап» — на карточке группы (список) и/или на выбранном маркере
     матрицы
- **Плейсхолдер-контент:** группы построены из элементов Screen 1 (Inbox), чтобы показать
  сквозную связность JTBD-2/JTBD-4 (счётчик = число исходных сообщений):
  | Группа | Частота | Value | Effort | Квадрант | Ручная корректировка | Состояние |
  |---|---|---|---|---|---|---|
  | Экспорт данных (CSV/Excel) | ×2 (@nastya_dev + Павел Т.) | 4 | 2 | Быстрая победа | нет | в роадмапе (In Progress) |
  | Тёмная тема | ×2 (Анна Р. + Игорь П., дубль) | 3 | 1 | Быстрая победа | нет | — |
  | Производительность при загрузке файлов | ×1 (Дмитрий Ковалёв) | 4 | 3 | На рассмотрении | нет | — |
  | 2FA / безопасность входа | ×1 (Ольга Верещагина) | 5 | 4 | Крупная ставка | да — Марина подняла вручную выше авто-ранга, т.к. это блокер для конкретного клиента | — |
- **Решения с обоснованием:**
  - Список групп и матрица показаны одновременно (split-view), а не как отдельные экраны
    по табам — задание design-generator явно требует «Backlog — группы + матрица
    Value×Effort» как один экран; ia.md sitemap перечисляет их как два под-пункта, но
    User Flow (шаги 5–9) проходит их последовательно в рамках одного визита на Backlog без
    указания на смену маршрута/URL — трактуем как один экран с двумя панелями (см. также
    заметку в разделе «Противоречия»).
  - Квадранты матрицы подписаны общими терминами метода Value×Effort, а не оставлены без
    подписи — research.md §8 явно рекомендует lightweight Value×Effort как метод
    приоритизации для команд 3–15, подписи квадрантов — стандартная визуализация метода, не
    отсебятина по функциональности.
  - Значок «скорректировано вручную» обязателен по ia.md шагу 8, реализован как визуальный
    бейдж на маркере/карточке, а не отдельное состояние экрана.
- **Smoke-test:** не применимо (документный проход). Внутренняя проверка: группы
  прослеживаются к исходным Inbox-элементам, Value/Effort проставлены для каждой,
  CTA «Добавить в роадмап» присутствует и ведёт к Screen 3.

### Screen 3: Roadmap (Kanban)

- **Frame ID:** не применимо (документный проход)
- **Назначение:** Закрывает **JTBD-3** («понять, за что браться» — прозрачный статус) и
  **JTBD-5** («показать команде/юзерам, почему так» — наглядная модель прогресса). Прямое
  соответствие в ia.md таблице «Связь с JTBD».
- **Строго по допущению D1 из ia.md:** ровно 3 колонки — «To Do» / «In Progress» / «Done».
  Публичность роадмапа для конечных пользователей — вынесена в v2 (OQ-2 ia.md, фича #9
  research.md §7) и в этот макет не включена.
- **Main CTA:** «Переместить пункт в следующий статус» (drag-and-drop карточки между
  колонками) — ia.md User Flow шаг 10: «перетаскивает пункт в колонку «In Progress»».
- **Layout pattern:** F-pattern. Обоснование: канбан-доска — это dashboard-паттерн
  (алгоритм design-generator прямо относит dashboard к F), сканирование идёт по колонкам
  слева направо, внутри колонки — сверху вниз по карточкам.
- **Структура по зонам (Desktop: Top / Left / Center):**
  - **Top:** тот же shell
  - **Left:** side-навигация, пункт «Roadmap» активен
  - **Center:** 3 колонки Kanban в ряд, с заголовком-счётчиком на каждой
- **Ключевые блоки (сверху вниз / слева-направо):**
  1. Top bar + Left sidebar (Roadmap активен)
  2. Заголовок «Роадмап»
  3. Три колонки: «To Do» (счётчик), «In Progress» (счётчик), «Done» (счётчик)
  4. Карточка пункта роадмапа (в каждой колонке): название темы (из Backlog-группы),
     приоритетный бейдж (Value/Effort или ранг), счётчик частоты обращений, мини-иконки
     источников
- **Плейсхолдер-контент** (продолжение сквозного сценария из Screen 2):
  | Колонка | Карточка |
  |---|---|
  | To Do | «2FA / безопасность входа» — Value 5 / Effort 4, ×1 обращение, скорректировано вручную |
  | To Do | «Тёмная тема» — Value 3 / Effort 1, ×2 обращения |
  | In Progress | «Экспорт данных (CSV/Excel)» — Value 4 / Effort 2, ×2 обращения (Марина уже начала неделю с этого пункта) |
  | Done | «Push-уведомления о новых комментариях» — реализовано в прошлом спринте (пример завершённого пункта для полноты доски, не связан напрямую с текущей партией фидбэка из Screen 1) |
- **Решения с обоснованием:**
  - Ровно 3 колонки — прямое наследование допущения D1 из ia.md, без «улучшения» (задание
    явно требует наследовать допущения как есть).
  - Карточка показывает Value/Effort и частоту, а не только название — это прямая
    реализация JTBD-5 («показать команде... почему так») — прозрачность приоритета должна
    быть видна прямо на доске, а не только в Backlog.
  - Пункт в колонке «Done» добавлен для полноты канбана (иллюстрация состояния, что доска
    не «вечно пустая» справа) — сознательная реконструкция для реалистичности макета, не
    факт из источников; помечено явно в самой строке таблицы.
- **Smoke-test:** не применимо (документный проход). Внутренняя проверка: ровно 3 колонки
  (соответствие D1), пункты прослеживаются к группам из Screen 2.

## Визуальная система

Тональность и принципы выводятся из brief.md (§«Контекст и продукт», §«Целевая аудитория»)
и research.md (§2 SWOT — конкуренты вроде Productboard воспринимаются как «тяжёлые» для
малых команд; персона Марина работает «по понедельникам», т.е. быстро и под нагрузкой).
Это B2B-инструмент для PM и небольших команд (3–15 чел.), не consumer-продукт.

- **Тон:** спокойный, деловой, без игривости и ярких акцентов. Продукт должен «не
  утомлять» при разборе десятков сообщений подряд (JTBD-2) — минимум визуального шума,
  максимум внимания на данные.
- **Плотность информации:** средне-высокая в списках (Inbox, Backlog) — PM должен успевать
  сканировать много строк за раз (research.md §5, сценарий «~80 сообщений за неделю»); ниже
  плотность в Empty state и на карточках Roadmap — там задача не «прочитать много», а
  «понять один факт».
- **Палитра (уровень принципов, semantic-роли, без hex):**
  `surface/primary`, `surface/secondary` (фон карточек/панелей), `text/primary`,
  `text/secondary`, `text/meta` (даты, счётчики), `border/subtle` (разделители строк
  списка), `accent/brand` (используется точечно — главный CTA, активный пункт навигации),
  `semantic/success`, `semantic/warning`, `semantic/danger`, `semantic/info` (баннеры,
  бейджи «скорректировано вручную», предупреждения об ошибке группировки). Конкретные
  значения токенов (hex/размеры) — не зона ответственности этого артефакта, это работа
  `/ds-tokens`.
- **Типографическая иерархия (4 уровня):** заголовок экрана (H1) → заголовок секции/группы
  (H2/подпись карточки) → основной текст (body, текст фидбэка/названия пунктов) → мета-текст
  (даты, счётчики, источники) — мельче и приглушённее body.
- **Принципы состояний:**
  - **Default / hover / active / selected** — для строк списка и навигации, hover должен
    быть едва заметным (спокойный тон), не ярким.
  - **Empty** — отдельная композиция (Screen 1.empty), не «пустой список без объяснения».
  - **Error / warning** — баннер в верхней части центральной зоны (ia.md Edge Case 2), тон
    `semantic/danger`/`semantic/warning`, не блокирует остальной интерфейс.
  - **Manual override** — визуально отличается от авто-рассчитанного состояния (бейдж
    «скорректировано вручную» в Backlog/Roadmap) — пользователь должен видеть, где
    вмешался человек, а где сработал алгоритм (доверие к группировке, риск из brief.md
    §«Риски»: «если группировка ошибается, PM теряет доверие быстрее»).
  - **In roadmap** — группа в Backlog, уже добавленная в роадмап, несёт бейдж «в роадмапе»
    (симметрично бейджу «скорректировано вручную»): пользователь видит, что пункт уже
    передан дальше, и не отправляет его повторно.

## Заметки о противоречиях/пробелах входа

1. **Backlog как один экран vs sitemap с двумя под-пунктами.** ia.md Sitemap перечисляет
   «Группы/Темы» и «Приоритизация (Value×Effort)» как два отдельных под-узла Backlog; ia.md
   User Flow (шаги 5–9) проходит их последовательно в рамках одного визита без явного
   указания на переход между отдельными URL/экранами. Задание на этот проход прямо требует
   собрать их в один экран («Backlog — группы + матрица Value×Effort»). Решение здесь —
   следовать заданию (один экран, split-view), но это расхождение с буквальным прочтением
   sitemap ia.md стоит уточнить у `ia-architect`, если экран будет реализовываться в коде/
   Figma по-настоящему (не правил ia.md сам, как предписано).
2. **D1 (3 статуса роадмапа) унаследовано как есть**, без «улучшения» — ia.md сам помечает
   это как допущение, требующее подтверждения заказчика (OQ-1). brief.md содержит тот же
   открытый вопрос («Что именно входит в базовый роадмап MVP») — это не новое противоречие,
   а один и тот же открытый вопрос, дублированный в двух артефактах. Публичность роадмапа
   (OQ-2) осознанно не включена в макет.
3. **Конкретный текст фидбэк-сообщений и имена авторов — не факты из research.md.**
   research.md даёт контекст персон (Марина: SaaS-стартап, Telegram-комьюнити + Slack-канал
   поддержки) и обобщённые сценарии (research.md §5), но не приводит буквальных цитат
   конечных пользователей продукта Марины (только цитаты самой Марины/Антона/Лены как
   персон-интервьюируемых). Тексты сообщений во всех трёх happy-path экранах —
   реалистичная реконструкция под этот контекст (типичные SaaS feature requests: экспорт,
   тёмная тема, производительность, 2FA), не «Lorem ipsum» и не выдуманные факты о
   продукте/рынке. Реконструкция распространяется и на седьмое сообщение (Павел Т.,
   выгрузка в Excel), добавленное при ревью для прослеживаемости группы «Экспорт данных ×2»
   к двум видимым сообщениям. Явно фиксирую это здесь, чтобы не спутать с найденными в
   ресёрче данными.
4. **D2 (один workspace на команду)** отражено в макете как отсутствие переключателя
   продуктов/команд в Top bar (только имя workspace) — расхождений с ia.md нет, фиксирую
   для прозрачности решения.

## Технический долг / Отложено

- **Settings (Интеграции / Правила захвата / Участники)** — присутствует в ia.md sitemap и
  в левой навигации всех макетов как пункт меню, но сам экран **вне скоупа этой итерации**
  (жёсткое ограничение задания — только 4 экрана). Требуется отдельная итерация
  design-generator.
- **Login и Onboarding wizard** (ia.md User Flow шаг 1; Edge Case 3 «первый запуск») — не
  специфицированы, вне скоупа этой итерации.
- **Error state (ia.md Edge Case 2, полная таблица из 4 типов ошибок)** — только принципы
  визуализации ошибок описаны в разделе «Визуальная система» (баннер, semantic/danger), но
  отдельные Frame для error state **не создавались** — вне скоупа (задание фиксирует ровно
  4 экрана, error state в их число не входит).
- **Публичный роадмап / changelog для конечных пользователей** (research.md фича #9, ia.md
  OQ-2) — v2, не проектировался.
- **RICE / полный scoring-фреймворк** (research.md фича #11) — v2, не проектировался; MVP
  сознательно ограничен Value×Effort.
- **Figma-рендер, Frame ID, привязка к компонентам DS, Variables, Light/Dark mode
  smoke-test** — не применимо в этом документном проходе. Требуется отдельный проход
  design-generator в режиме работы с Figma MCP, когда MCP-доступ и DS-библиотека будут
  подтверждены.
- **Мобильная/адаптивная версия** — не запрошена; brief.md фиксирует платформу как desktop
  web без явного требования responsive, поэтому mobile-версия макетов не создавалась.
